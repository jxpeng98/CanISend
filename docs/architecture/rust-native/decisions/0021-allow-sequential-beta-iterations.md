# ADR-RN-0021: Allow exact sequential Beta iterations

**Status:** Accepted

**Date:** 2026-09-03

**Decision owner:** CanISend maintainer

## Context

Public `v1.0.0-beta.1` is independently verified, recorded as qualified, and protected by the
active feature freeze. Release owners need one additional private Beta source checkpoint to finish
CLI, Agent v4 Skills, MCP, and Workspace v4 readiness before RC.1. The existing state machine
allows sequential Alpha and RC candidates but rejects a same-stage Beta transition.

Rewriting Beta.1 evidence or treating it as qualification for changed Beta.2 bytes would break
release identity. Moving directly to RC.1 would also make the next checkpoint carry readiness work
that should be proven while the product is still in Beta.

## Decision

1. The 1.0 line may prepare an exact `beta.N -> beta.(N+1)` transition. The release line must be
   unchanged, both versions must omit build metadata, and the numeric iteration must increase by
   exactly one.
2. The current Beta must have a canonical qualified tag, source commit, signed-matrix run, and
   signing-target record. Feature freeze must be active at a valid baseline.
3. `release/qualification-ledger.json` keeps `beta` as the active/latest slot. A sequential
   transition appends the exact qualified record to ordered `beta_history`, then resets only the
   active slot to `{ "status": "pending" }`.
4. Beta readiness, contract freeze, feedback, cohort evidence, and the feature-freeze baseline
   remain historical or active authorities and are not regenerated by Beta iteration.
5. Beta.2 qualification is a separate operation against its exact signed assets. RC.1 and Stable
   require the latest active Beta to be qualified and never use `beta_history` as a fallback.
6. Stage preparation remains dry-run-first and transactionally updates only its controlled source
   projections. It does not create a tag, dispatch a workflow, publish a release or package, or
   claim qualification.

## Consequences

- Beta.1 stays immutable and auditable while Beta.2 receives a distinct source and evidence slot.
- Skipped, repeated, downgraded, cross-line, malformed, build-metadata, unqualified, or
  noncanonical transitions fail before files change.
- The existing feature-freeze exception protocol applies to changed nonautomatic source files.
- RC.1 is deferred until the latest active Beta and the existing pre-RC evidence gates pass.

## Rejected alternatives

- **Move directly to RC.1:** rejected because the remaining readiness work belongs to a Beta
  checkpoint and RC qualification should start from a complete active Beta.
- **Overwrite the Beta.1 ledger record:** rejected because it would erase qualified release
  history.
- **Treat Beta.1 qualification as Beta.2 qualification:** rejected because changed bytes require a
  distinct tag, source, run, assets, and review.
- **Add a new release command or ledger schema:** rejected because the existing transition and
  canonical v1 ledger can represent the state with one optional history field.
