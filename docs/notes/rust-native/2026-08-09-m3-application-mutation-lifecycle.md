# M3 guarded Application mutation lifecycle

Date: 2026-08-09

CanISend now implements the first complete clean-v4 Requirement-to-Deliverable mutation loop for
either built-in Pack in one neutral Workspace.

## Implemented operations

- `requirement.extract.preview/commit` appends deduplicated Pack-qualified proposals that equal
  exact spans in one current Source already associated with the Application; private local-file
  and text-PDF Sources require explicit read consent.
- `requirement.confirm.preview/commit` decides every exact current proposed Requirement once.
- `plan.propose.preview/commit` creates a Host Agent-authored draft Plan only after Requirement
  decisions are complete.
- `plan.confirm.preview/commit` records explicit User authority over the exact draft Plan.
- `deliverable.draft.preview/commit` stores reviewed private draft bodies as content-addressed
  blobs and moves them to `review-required`.
- `deliverable.revise.preview/commit` replaces one exact Deliverable revision without changing its
  identity.
- `deliverable.audit` reads current private bodies only after explicit private-read consent.

The App facade owns validation and mutation. Tauri, the TypeScript bridge, and MCP are typed
adapters over that facade. MCP now publishes 29 clean-v4 tools: 21 read/preview tools and eight
guarded commits. The standalone CLI remains body-free for these resource families and does not
claim mutation parity until it can preserve an explicit approval boundary across its process
model.

## Approval and integrity boundary

Each preview token is generated by the shared CSPRNG broker, expires after ten minutes, is bounded
by the 16-entry capacity, and is tied to the exact Workspace, Pack, Application ID, Application
revision, snapshot digest, operation and preview digest. Denial, replay, wrong Application and
stale revision paths fail without authoritative mutation. Draft and revised bodies remain private
Blob content and are not returned by list/show operations.
