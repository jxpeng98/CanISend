# CanISend 1.0 release roadmap

**Status:** Active — Alpha product completion

**Decision date:** 2026-07-25

**First intended public version:** `1.0.0-alpha.1`

**Current source baseline:** `1.0.0-alpha.2`; the 1.0 line was activated at `1.0.0-alpha.1` from
`304072a`

**Current public checkpoint:** `v1.0.0-alpha.2` at
`d091d147390474514145b154b88b2cf443e6f7c1`, published as a prerelease on 2026-07-26

**Authority:** [ADR-RN-0014](../../architecture/rust-native/decisions/0014-start-the-unified-product-at-1.0-alpha.md)

## 1. Outcome

Release CanISend 1.0 as one local-first Rust-native product with:

- a standalone CLI and Agent v2 interface for terminal, Codex, Claude, scripts, and other hosts;
- a macOS-first native GUI over the same typed application facade and workspace;
- supplied URL and local Markdown, text, JSON, CSV, and text-PDF intake without requiring an API;
- a version-matched GUI-to-terminal CLI installation, migration, update, rollback, and uninstall
  lifecycle;
- manual, privacy-preserving update checks;
- no Python, Node.js, Java, external SQLite, external Typst executable, or browser runtime for end
  users; and
- bounded preparation and export of application materials without application submission.

The current public version is an Alpha because the GUI vertical slice is usable but does not yet
cover the complete application workflow or final native qualification matrix.

## 2. Version and channel policy

| Stage | Version | Entry condition | Meaning |
|---|---|---|---|
| Release-line activation | `1.0.0-alpha.1` in source | 0.7 history preserved and all active release state reset atomically | Development authority has moved to 1.0 |
| Alpha publication | `v1.0.0-alpha.N` | Alpha product, package, lifecycle, and evidence gates pass | Early macOS GUI and five-target CLI evaluation |
| Beta | `v1.0.0-beta.1` | Alpha feedback triaged; intended 1.0 surface complete | Contract and format freeze begins |
| RC | `v1.0.0-rc.1` | Feature freeze active; Beta evidence complete | Only blockers, evidence, and docs may change |
| Stable | `v1.0.0` | Required clean-tag RC matrices and release evidence pass | Supported 1.0 product |

Rules:

1. There is no public `0.8` line.
2. The public 1.0 line starts at `1.0.0-alpha.1`; a direct jump from Alpha to RC is prohibited.
3. Additional Alpha versions are allowed only sequentially and must have a stated reason.
4. Beta, RC, and Stable promotion use the checked-in stage transition tool and qualification
   ledger.
5. A version change does not itself publish a tag, release, package-manager entry, or update.
6. Preview update checks may see prereleases; Stable update checks ignore prereleases.

The release-line activation implementation must create a versioned `release/history/0.7/`

Historical evidence proves how `0.7` was qualified. It is useful prior evidence for control design,
but it does not count as `1.0` Alpha/Beta/RC artifact evidence.

## 4. Workstreams

### A. Release authority and version activation

- Add a dry-run-first `release activate-line v1.0.0-alpha.1` operation.
- Accept only a new `X.Y.0-alpha.1` line with no build metadata.
- Require a clean worktree for `--write`.
- Archive and hash the active `0.7` release state.
- Atomically update:
  - workspace version and exact internal dependency pins;
  - root and fuzz lockfile workspace package versions;
  - active qualification ledger;
  - active support policy;
  - release notes heading and 1.0 product text;
  - feature-freeze state;
  - Alpha/Beta readiness state;
  - stage-aware release checks; and
  - documentation that the source gate validates literally.
- Emit a deterministic before/after plan containing every controlled file digest.
- Never create a tag, push, publish, upload, or edit a package-manager repository.

The new Alpha ledger begins in `pre-beta`, with Stable authorization false, feature freeze planned,
all 1.0 artifact evidence pending, no RC records, and Alpha-current release notes.

### B. GUI product completion

The Alpha must include a coherent, safely bounded workflow rather than every long-term GUI feature.
The minimum `1.0.0-alpha.1` GUI scope is:

- workspace create/register/switch/status/check/backup and safe registry removal;
- job create/list/show/archive;
- supplied URL and local Markdown/text/JSON/text-PDF import;
- workflow start/status and clear copyable handoff to Agent v2;
- Command line install/migration/update/uninstall with rollback and digest protection;
- manual Stable/Preview update check;
- body-free diagnostics;
- close/reopen persistence; and
- explicit labels for operations that remain CLI/agent-host only in Alpha.

Before Beta, complete:

- workspace restore and projection repair;
- workflow begin/complete/rerun;
- criteria, profile evidence, match, and plan confirmation;
- discovery and agent-task lifecycle;
- documents, review dispositions, package readiness, render, and export; and
- complete ordinary CLI-to-GUI mutation coverage.

### C. macOS packaging and lifecycle

Alpha packaging must:

- build the GUI and version-matched CLI from the same source/version;
- place the CLI at `CanISend.app/Contents/Resources/bin/canisend`;
- include licenses, notices, privacy guidance, and exact executable hashes;
- use a free ad-hoc integrity signature for nested executables and the outer app;
- state that the build is not Developer ID signed or notarized;
- launch and complete the synthetic workflow on Apple Silicon;
- test CLI install, migration, update, uninstall, and rollback in a disposable macOS user profile;
- retain all external workspaces after app and managed-CLI removal; and
- record body-free evidence against the exact packaged bytes.

Alpha manifests intentionally contain no Intel GUI release evidence. A scheduled Intel runner
keeps compile regressions visible without authorizing publication or support. Beta and later
restore exact-candidate compile-only evidence; native Intel qualification remains mandatory before
the product makes an Intel GUI runtime support claim.

### D. Standalone CLI release matrix

The existing five CLI targets remain:

- `aarch64-apple-darwin`;
- `x86_64-apple-darwin`;
- `x86_64-pc-windows-msvc`;
- `x86_64-unknown-linux-gnu`; and
- `x86_64-unknown-linux-musl`.

The 1.0 manifest must distinguish CLI support from GUI support. Windows and Linux GUI packages are
deferred and cannot be implied by the presence of a standalone CLI archive.

### E. Documentation and agent integration

Update user guidance around one 1.0 product:

- GUI installation and the terminal CLI bridge;
- CLI-only installation for non-GUI platforms;
- workspace sharing with Codex and Claude;
- URL/PDF/file intake;
- update checking and preview-channel semantics;
- ad-hoc signature verification and trust limitations;
- backup, rollback, uninstall, and workspace retention; and
- exact Alpha limitations and recovery paths.

Host packs remain generated by the installed binary. GUI automation does not replace Agent v2.

## 6. Verification tiers

Use the smallest tier that proves each edit:

1. **Focused:** affected crate tests, formatter, relevant Clippy target, JSON parsing, and
   `git diff --check`.
2. **Source gate:** `cargo run -p xtask --locked -- release check` plus the fast workspace CI.
3. **Native Alpha gate:** exact packaged CLI/app matrices, launch, lifecycle, accessibility, and
   workspace-retention tests.
4. **Extended qualification:** fuzzing, advisory/license checks, free-signature evidence,
   provenance, package-manager lifecycle, clean-tag RC matrices, and Stable authorization.

Long-running fuzz and dependency assurance stay out of the ordinary edit loop unless a focused
local reproduction is required.

## 8. Release blockers

The Alpha must not be published while any of these is true:

- source, internal dependency, GUI, bundled CLI, manifest, or ledger versions disagree;
- 0.7 historical evidence cannot be verified by digest;
- the GUI bundle contains a different CLI or an unrecorded executable;
- URL, file, PDF, registry, or installer bounds can be bypassed by malformed local fixtures;
- managed CLI replacement/uninstall can destroy an unmanaged or externally changed command;
- app uninstall or registry removal can delete a workspace;
- private bodies appear in update checks, routine diagnostics, registry data, or release evidence;
- the packaged app fails its claimed macOS launch/workflow/reopen lifecycle;
- ad-hoc signature limitations or platform support claims are misleading; or
- the release notes omit known Alpha limitations and rollback instructions.
